# خطة ترحيل العملاء الحاليين: مجموعات + كيانات قانونية (متوافقة مع الخلف)

> **المبدأ:** لا تُمس بيانات العملاء الحالية. كل عميل قائم يبقى كما هو (بكوده، اسمه،
> رقمه الضريبي إن وجد) حتى يقرر المحاسب/الإدارة الربط. لا تخمين في الانتماءات.

## 1. ما الذي يتغير في قاعدة البيانات (migration `20261021120000_add_customer_groups_legal_entities`)

| الكائن | التغيير | التوافق مع الخلف |
|---|---|---|
| `CustomerGroup` | جدول جديد (code فريد, name, nameAr, active, version, ...) | لا يمس العملاء الحاليين |
| `CustomerGroupMember` | جدول ربط M:N (groupId + customerId فريدان معاً) | لا يمس العملاء الحاليين |
| `CustomerLegalEntity` | جدول جديد (code فريد, name, **taxRegistrationNo فريد**, عنوان فوترة + عنوان ETA, receiverType/Id) | لا يمس العملاء الحاليين |
| `Customer.legalEntityId` | عمود جديد nullable + FK (RESTRICT) | العمود null لكل العملاء الحاليين — سلوكهم القديم مطابق تماماً |
| `Customer.taxRegistrationNo @unique` | **يبقى كما هو** — لا حذف، لا تغيير | القيد الحالي محفوظ: عميل مستقل = رقم فريد |

**لا يوجد أي تعديل كتابي على بيانات العملاء الحالية في هذه الخطوة.**

## 2. الفرق بين المسارين — لماذا لا يكسر النظام شيئاً

| الحالة | قبل | بعد (بدون تدخل) |
|---|---|---|
| عميل برقم ضريبي خاص (فوترة باسمه) | يفوتر باسمه ورقمه | **نفس السلوك تماماً** (لا كيان مرتبط) |
| عميل بلا رقم ضريبي | ETA يعامله P أو يرفض B بدونه | **نفس السلوك** (لا كيان مرتبط) |
| عميل مرتبط بكيان (جديد) | — (لم يكن ممكناً) | يفوتر بالاسم القانوني ورقم الكيان وعنوانه |

## 3. مسار الترحيل التصاعدي (إضافي فقط، لا يمس القائم)

1. **استيراد المجموعات** (`customer_groups`) لقيم العلامات المعروفة من مصدر 366 —
   أسماء حصرية مثبتة من فريق المبيعات (JAZ، Four Seasons، ...). لا تختلق علامات.
2. **استيراد الكيانات القانونية** (`customer_legal_entities`): لكل شركة في بيانات 366
   كيان واحد باسمها القانوني ورقمها الضريبي **مرة واحدة**.
3. **ربط الفنادق** بالكيان عبر `legal_entity_code` في ملف `customers` (أو PATCH يدوي).
4. عند الربط، يُمسح رقم الضريبة من صف الفندق تلقائياً مع **سجل تدقيق** — لأن الملكية
   انتقلت للكيان. (لا يُمسح أي رقم من عميل غير مربوط.)

## 4. سجلات تحتاج قراراً تجارياً/محاسبياً قبل الربط (قائمة فحص)

لا تُنجز هذه تلقائياً — كلها تنتظر تأكيداً بشرياً:

| الحالة في المصدر/النظام | القرار المطلوب |
|---|---|
| عميلان قائمان برقم ضريبي **واحد** مستقلّين (غير مربوطين) | أيهما الكيان القانوني؟ هل يُدمج الآخر عليه؟ (القيد الحالي يمنع حتى اليوم وجود رقمين — تحقق من بيات البيانات) |
| عميل حالي برقم ضريبي لكنه يتبع شركة أم | هل يُنشأ كيان باسم الشركة الأم وينقل الرقم؟ موافقة المحاسب على النقل |
| فندق بلا رقم ضريبي في المصدر | هل يُحصّل الرقم لاحقاً؟ أم يبقى P/ورقي؟ (قرار سياسة فواتير) |
| عدة فنادق لنفس الشركة الأم | تأكيد الاسم القانوني الواحد (متطابق مع البطاقة الضريبية) + عنوان الفوترة الرسمي |
| العلامة التجارية | من يقرر العضوية (فندق JAZ → علامة JAZ)؟ لا يُستنتج من الاسم وحده (قد يكون فرعاً لمدير شركة مختلفة) |

**أداة تحديد القائمة** (على نسخة القراءة، لا تعديل):
```sql
-- كل رقم ضريبي مسجل على أكثر من عميل مستقل (ممنوع اليوم — تحقق من التكرار الفعلي)
SELECT "taxRegistrationNo", count(*) FROM "Customer" WHERE "taxRegistrationNo" IS NOT NULL GROUP BY 1 HAVING count(*) > 1;

-- كل عميل عليه رقم ضريبي (مرشح ليصبح كياناً قانونياً أو يُربط بكيان)
SELECT code, name, "taxRegistrationNo" FROM "Customer" WHERE "taxRegistrationNo" IS NOT NULL ORDER BY "taxRegistrationNo";

-- كل عميل من غير رقم ولا كيان (يحتاج قرار سياسة الفوترة)
SELECT code, name, type FROM "Customer" WHERE "taxRegistrationNo" IS NULL;
```

## 5. الفوترة والـ ETA بعد الترحيل

- **الفواتير الصادرة سابقاً:** مجمّدة (snapshot) — لا تتأثر نهائياً. إن وُجد عميل
  رُبط بكيان بعد إصدار فواتير باسمه، ففواتيره القديمة تبقى باسمه (قانونية كما صدرت).
- **الفواتير الجديدة:** تُؤخذ بيانات المشتري من الكيان القانوني المربوط عند الإصدار
  (الاسم القانوني، الرقم الضريبي، عنوان الفوترة) — وتُجمّد على الفاتورة.
- **قبول ETA:** مع `receiver_type=B` ورقم ضريبي 9 أرقام على الكيان، يتحقق
  `receiver.id` بنجاح. الفندق بلا كيان ولا رقم يبقى على السلوك الحالي (P أو رفض B).

## 6. قيود لن تُكسر

- `CustomerLegalEntity.taxRegistrationNo` فريد → **يمنع** رقمين على كيانين — وهو
  المطلوب (`الرقم الضريبي مسجل لكيان قانوني آخر`).
- `Customer.taxRegistrationNo` فريد يبقى → عميل مستقل برقمه (فوترة باسمه) محمي.
- `external_ref` فريد يبقى → هوية صف المصدر ثابتة، منفصلة عن كود CUS والانتماء.
- لا اختلاق: أي رقم ضريبي/هوية ناقص يبقى فارغاً، وتبقى الإشارة "بانتظار متابعة" في
  كارت العميل (رسالة واجهة) حتى يُحصَّل من المصدر.

## 7. غير قابل للترحيل التلقائي (يحتاج قراراً أولاً)

1. أي عميل يشترك رقماً ضريبياً مع آخر دون كيان قانوني موحّد — القيد الحالي يمنع أصلاً؛
   إن وُجد بالبيانات فمعالجة يدوية بمشاركة المحاسب.
2. انتماء الفنادق للعلامات — يُستورد فقط بعد اعتماد القائمة من فريق المبيعات.
3. أرقام الضريبة الناقصة في المصدر — لا يُختلق بديل عنها.
4. الفواتير الصادرة — لا تُعدّل (قانونياً مجمّدة).
